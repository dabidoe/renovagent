# Bathroom MVP implementation plan

**Phase 0 proposal · November 10, 2026**

Start only after product-owner review. The smallest release candidate is a free iPhone planner for **one like-for-like vanity replacement in an existing bathroom**. Keep the room shell, openings, and service locations. Use a simple before/after plan. Treat concealed conditions, confirmed connection mismatches, structural work, and service relocation as outside the supported scope. The project and room contracts should generalize through playbooks. No store account, cloud sync, model API, app-generated checkout, payment, or qualified technical release is part of this slice.

## End-to-end reference case

1. Create a bathroom project on-device. Enter tape dimensions and a measured vanity bay, or scan with RoomPlan on a supported device and review the result. Record a separate tape value for the critical bay width. Add an optional site photo. Reopen the project offline.
2. Select the existing vanity in the plan or list and choose **Replace**. Keep the original baseline. Build a draft scope from the narrow, versioned bathroom recipe. The owner can tell which work is included and which conditions are unknown.
3. Share a product URL from Safari or a supported retailer app. Attach the pending link to the vanity replacement. Enter or confirm the exact variant, manufacturer dimensions and relevant connection specs, with a source. Record homeowner/contractor supply status. A manual paste path covers unavailable share payloads.
4. Show the candidate in the proposed plan and run supported deterministic comparisons. Unverified or mismatched connections remain open. Export a redacted, named contractor-review packet with the scope, evidence, dimensions and open questions. The owner records the contractor's returned response against the packet, with its source and limits.
5. Prepare a purchase list for the current, reviewed selection. Show the exact variant, quantity, buyer and merchant link. If the width or SKU changes, the current review and affected list lines become stale. The old packet remains reproducible as history. The buyer can open the merchant link to handle their own checkout.

## Concrete acceptance tests

| Test | Pass condition |
| --- | --- |
| **Shared bridge parity** | Run existing rectangle/L-shape, unknown height, curved/multi-space and commerce fixtures in Node and the iPhone bridge. Match normalized units, IDs/refs where fixture-stable, typed error codes, decisions, and stale descendants for the same inputs. An unequal fixture result blocks launch. Capture cold launch, bridge time and peak memory on the oldest approved device. |
| **Local transactions** | In airplane mode create a project, attach a photo, record a fact and reopen after process termination. Inject termination between blob stage and manifest replacement. The last committed version opens with matching digests and no dangling references. Retry the exact command after a lost response and get one mutation; changed content with the same ID fails. Two same-base edits produce one commit and one conflict. |
| **Device capture and correction** | On physical LiDAR hardware record an asymmetric room with one opening. In the normalized plan the opening appears on the correct wall and orientation is preserved. Compare three consequential dimensions with tape and record discrepancies, OS/device and fixture limitations. Keep a mismatch visibly unresolved until corrected. On non-LiDAR, denied camera or interrupted capture, save via tape input without resetting the project or inventing measurements. |
| **Synthetic vanity test** | Use a tape-confirmed **30 in** bay and a sourced **24 in** variant. Shared conversion produces **762 mm** and **609.6 mm**. The dimensional comparison can pass while the unknown connection stays blocked. After documented contractor review for that revision, the list contains exactly one correct variant, quantity one and the assigned buyer. Changing the bay to **23 in** stales the prior review and excludes the line. A new SKU requires review even at the same dimensions. The original packet still shows the original inputs. This test checks arithmetic and workflow, not installability of real products. |
| **Open and import a retailer link** | Run the [payload/device matrix](RETAILER_INTEGRATIONS.md#acceptance-evidence-to-collect). Share two distinct variants of the same product and save one twice. Expect two distinct pending references and one deduplicated replay. Cancel leaves no record. A malformed or multi-link payload cannot create an ambiguous selection. |
| **Redaction and revisions** | Preview and export PDF/CSV with the same issued revision. Default packet contains only explicitly selected derivatives and fields. Inspect the bytes for address, location metadata, original media, private rates and excluded lines. After edit, an old contractor response cannot be recorded as current review. Contractor feedback is attributed owner-recorded evidence, with no identity-verification badge. |
| **Free-tier and action boundary** | Instrument a complete online run and repeat in airplane mode. Before explicit outbound user action, expect zero app calls to Renovagent, model providers or merchants. After tapping an approved link, only open it with the system. No merchant write, checkout automation, payment or order record. Missing support or bad connectivity never starts a cloud fallback. |
| **Web preservation** | Run `npm test`, `npm run build`, and `npm run ui:check`; run the Mongo-backed suite on disposable local data if shared contracts or API code change. Reopen an existing legacy workspace and current project/studio share fixture. Report pass/fail, skipped tests and device coverage separately. Existing canonical commands, hosted API and MCP proposal permissions must retain their current behavior. |

## Product-owner decisions before implementation

1. **Offline and distribution promise.** Approve native SwiftUI plus a bundled shared-domain proof, iOS 17 minimum as the starting assumption, manual workflow on non-LiDAR devices, and the fallback decision if the bridge fails. Confirm Apple developer team, signing, physical test devices, and internal TestFlight versus direct device testing.
2. **Workflow and buyer.** Approve the single-room, existing-footprint vanity slice, schematic 2D visual, manual entry/scan correction and spec evidence. Decide whether a second fixture or multi-room proof is needed after the first release candidate.
3. **Review semantics.** Approve PDF/CSV with attributed external feedback for MVP. Define whose response can move an item into the reviewed list, and confirm the user-facing distinction between planning review, verified contractor identity, purchasing and construction authorization.
4. **Privacy, backup and access.** Approve photo and export limits, protected storage, original media retention, device backup/deletion policy, default redactions, diagnostics and treatment of exports that recipients can forward.
5. **Reuse and distribution rights.** Approve existing OpenPlan3D-compatible import and narrow Zod bridge with notices. Confirm rights for any code, fonts, media or assets before shipping. Separately approve any external hackathon code import after commit-level review.
6. **Commercial boundary.** Confirm zero hosted inference/media/sync allowance at launch, named retailers for manual testing, and link-only purchasing. Any supplier connection or hosted review needs a separate owner decision and cost ceiling.
7. **Quality gates.** Agree on device/OS coverage, real bathroom test rooms and consent, scan correction policy, app size and performance budgets, and the evidence required to approve wider distribution.
