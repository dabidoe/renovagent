# Three-project example and live-demo specification

October 31, 2026. Proposed content and acceptance specification, not seeded project records. NYC/SF source assets and complete fixtures are not yet assembled. New Hutchinson photos/videos are pending from the owner. Do not copy these proposals into canonical physical facts as if observed.

## Shared example contract

Each case gets its own stable example template ID, original/reference media, scope/artifact IDs, source records and saved baseline. Opening a prepared example creates or resumes an isolated visitor working copy; it does not append duplicates to the owner's workspace. A reset affects that copy only. Hutchinson is an actual owner project and must not use the example reset path.

Example gallery cards show a room image, location, one-sentence goal and what can be explored. Keep the gallery small: **NYC · Bathroom / SF · Living room / Hutchinson · Your project**. Do not make visitors choose twenty capabilities or read a tour before opening a room. Public demo assets must be selected deliberately; do not expose private owner media merely because it is saved in the project.

Every case must populate **Room, Design, Work & costs, Products, Handoff** from the same selected project/revision. Numbers in screenshots, pins, sidebars, option comparisons and exports must share their calculation inputs. Prepared synthetic dimensions and bids remain identified as example data. Titles can be memorable; factual product/model/price/credential claims still need sources.

## 1. NYC — the work behind the bathroom

**Proposed case:** an apartment bathroom refresh, keeping the existing wet-area layout. This is a bounded refresh story, not a promise of apartment renovation approval.

**Opening brief:** “I want the oak vanity and dark tile look. Keep the plumbing where it is if we can.”

**What is visually different:** a compact bathroom, distinctive original finishes, one reference look, a vanity and floor that can each be selected. Do not reuse the landing hero as every room image. Use owned/licensed imagery or clearly identified generated example scenes; do not attribute a generated interior to a real apartment.

**Prepared content:**

- Original scene plus separately identified inspiration; owner preference is the oak finish, vanity form and floor appearance, not an assumed exact SKU match.
- Two useful options: retain the existing fixture where practical with a lighter refresh; replace the vanity/floor with a fuller refresh. Each has explicit inclusions/exclusions.
- Vanity package with fixture/top/faucet responsibilities and conditional supply lines, shutoffs, fittings, trap, fixings and sealant as applicable. Flooring includes substrate preparation, setting materials, grout, transitions/edge treatment and disposal where the recipe supports them.
- A product photo, exact source URL, specifications, pack/unit, dated price and match status for each selected sourced item. Clearly separate original-photo object, inspiration object, requirement and product candidate.
- Separate trade labor: work description and an established hours/rate or bid basis. Do not infer a pipe route or a labor duration from the image alone.
- Relevant property/building constraints belong to supplied context or a short open-question list. “NYC” is not permission to invent a building's rules, tenancy status or permit outcome.

**Key interaction:** tap the vanity, inspect supporting work, then keep it or change the selection. The project shows which material and labor lines are added/removed, saves the proposal and keeps the earlier revision available.

**Required assets:** at least two consistent original room views, one inspiration reference with provenance, two coherent concept views, product photos/links, calculation fixtures, one comparable example bid set or supplied real bid, and a handoff preview. A rendered scene must not silently change room geometry between options.

**Pass:** the bathroom example delivers more than a four-item shopping list; a change to the vanity does not unnecessarily rewrite unrelated flooring decisions. Every tab is populated and no click enters living-room or generic simulation defaults.

## 2. San Francisco — get the look with a sensible scope

**Proposed case:** a living-room wall/floor refresh using the supported living-room recipe. Broader structural or seismic work is outside this example unless separately implemented and sourced.

**Opening brief:** “I like this warmer look. Do I need to replace the floor, or can I get most of the change with paint?”

**What is visually different:** a living room with the original floor and furniture clearly visible, a distinct inspiration palette, and alternatives that demonstrate keeping versus replacing. Use a different scene from NYC and from the generic current example where feasible.

**Prepared content:**

- Original photos and reference look, with what the person likes recorded explicitly.
- At least two options: paint/repair while keeping the floor; replace the floor plus trim/transitions and related prep. A third finish option is useful only if it changes a real tradeoff.
- The complete work sequence including furniture/protection, surface preparation, existing floor removal if selected, new floor system, edge details and cleanup/disposal basis.
- Product/specification choices and dated source links; show why an alternative is appropriate rather than listing arbitrary catalog tiers.
- Material and labor totals on comparable terms, including what is unpriced. Quantities need supplied/fixture geometry; without it, show a useful work draft and the next measurement that would narrow the affected cost.
- One ready before/after or concept pair tied to the selected option. Keep furniture/location/camera consistent enough to make the decision legible.

**Key interaction:** choose “Keep the floor” then a replacement option; compare actual scope additions/removals, installation burden and cost. One subsequent “less expensive” change updates requirements/product leads and the handoff together where implemented.

**Pass:** a buyer can tell what the extra spend buys and what work disappears when retaining the floor. No unsupported generic “SF costs X% more” multiplier. The technical panel does not open half-bath plumbing fields.

## 3. Hutchinson — the real input and correction test

**Known prior direction:** the owner previously discussed an additional half bath in the living-room area and reported an existing basement half bath. Those are user-reported goals/context. No feasible service route, permitted configuration or construction-ready estimate is established by that history. Reconfirm the current live-demo task when the new media arrives.

**Opening brief:** use the owner's actual words and goal. Retain the original photo as the primary view. Do not manufacture the example room's dimensions or scope to make Hutchinson look complete.

**Useful first live result:** identify visible elements and propose a bounded next piece of work. Distinguish the existing room from the proposed addition and the inspiration. Let the owner correct one observation or mark something to keep. Save the correction and develop the affected task list. If the chosen task is within a supported refresh recipe, connect it to that recipe; an additional bathroom's feasibility needs a separate investigation scope.

The live presentation should prove new evidence, an owner correction, a saved revision and consumer-Muse continuity. It does not need to prove hidden pipe routes or an entire construction design. A targeted investigation packet can be useful; an invented confident estimate for an unsupported addition will weaken the demonstration.

**Media set to prepare when supplied:**

- A room-wide photo from two positions, with the same area identifiable between views.
- A close-up of the element being changed; optional existing visible connection/condition detail.
- One inspiration image/link and a sentence about the desired aspect.
- A short walkthrough clip if helpful. Proposed initial behavior: preserve the original and select a few time-stamped keyframes for image analysis. This is a feature requirement, not implemented video understanding.
- What stays, what changes, and any owner-known constraint. Measurements are welcome when available, not an intake requirement.

The owner's iPhone files must be tested directly before the rehearsal. Support/normalize the formats actually provided rather than requiring the owner to manually convert everything. A selected frame and still-photo upload should lead into the same evidence/analysis flow.

**Pass:** new owner media is attached to the correct actual project; source roles stay separate; a corrected observation persists; the next useful artifact references it; Muse and website show the same project/revision. No demo reset, fixture quantity or prepared-case bid overwrites owner records.

6. Cancel a change: return to saved state; no accidental command or model run.
7. Switch NYC → SF → Hutchinson → back: media, context and selections remain separated.
8. Reset prepared case: affects only that visitor's example copy. No reset action is offered for the actual owner project.
9. Run from 390 px and desktop: selected controls, popups, keyboard focus and cancel remain usable.
10. Ask Muse for one bounded revision: confirm the same project/artifact revision in the web view, with no approvals granted by the agent itself.
